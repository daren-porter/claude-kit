- **Guard the remaining unbounded `openSync` calls in session-start.js (2026-08-07).** A bounded read bounds bytes, not time: `openSync` on a FIFO blocks until a writer appears, and the security reviewer hung the hook for 5 seconds this way before killing it, against a file header that promises "Never blocks". S4 added the `statSync(...).isFile()` guard to its own helper only. Four pre-existing readers in that file still lack it: `countPendingKaizen` (the notes read), `findCompletedUnarchived`, the plan scan in `main()`, and `claudeMdSyncOffer`, which carries two of them (its `statSync` checks size and not `isFile`, so the asset `readFileSync` blocks just as an `openSync` would, and the version-marker `openSync` is unguarded). `hooks/kit-goal-lib.js:44-48` carries the guarded idiom with a comment naming the hazard. Not exploitable under the kit's trusted-workspace premise; it is a self-inflicted-hang risk, so fix it the next time that file is open. Use the atomic form for the sweep rather than copying S4's stat-then-open: open with `O_RDONLY | O_NONBLOCK` and check `fstatSync(fd).isFile()`, which closes the TOCTOU window the finishing security review noted and is a no-op for regular-file reads. `hooks/memory-lib.js`'s `readCapped` is now the in-repo copy of that atomic form, added 2026-08-08, and every file door in the memory tier uses it after a FIFO at the apply journal hung session start indefinitely.
- **Replace `process.exit(0)` after a stdout write with `process.exitCode = 0` (2026-08-07, count corrected same day).** Forcing the exit can discard a write still in flight on a pipe. **Seven sites, not the four first recorded.** Four carry the stdout shape: `session-start.js:604` (`:350` before the cross-project-memory blocks landed), `stop-docs-hygiene.js:106`, `branch-reaper-nudge.js:155`, and `kit-goal-stop.js:410`. Those three files' trailing `exit(0)` is a clean no-output path and needs no change. `hooks/kit-goal.js` already uses `process.exitCode` throughout and is the in-repo precedent to copy. Found and confirmed during the 2026-08-07 adoption pass (Scott fixed the same shape across six hooks in his kit); the seven-site count was verified on that pass's second run. Out of scope for the pass itself; fix on its own.

- **Trim what the orchestrator and the skills generate (2026-07-20, triaged 2026-08-07).** The token-profiler run (Piece 2, `tools/token-profiler.js`) settled where the kit's cost actually sits, and the answer splits by unit. In token **volume**, accumulation dominates: the orchestrator main thread is ~88% of cross-session tokens. In **dollars** the lever is the kit's own generated output, because cache-read bills at 0.1x while output bills roughly 5x. Two things follow, both closed rather than parked. A fresh-session nudge at Chapter or section boundaries would relieve context-window pressure, not spend, so it does not earn its complexity on cost grounds; the resume machinery (Chapters plus SessionStart) already exists if it is ever wanted for the window instead. And standing per-session context is a weak target for the same reason: the unused multi-K `Workflow` tool schema every session carries is volume, not dollars, so disabling it in `settings.recommended.json` would trade Workflow and ultracode session-wide for a rounding error (and no mechanism was confirmed to remove a tool's schema anyway, as a permissions deny blocks calls without reclaiming the tokens). What is left, and what this item is: trim what the kit actually *writes*. Dispatch prompts, Chapters, review reports, and close-out prose are output tokens at full price, generated fresh every effort.
